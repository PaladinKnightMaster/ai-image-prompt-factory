# EXP-019 v1.2.0 — Admission, Failure, and Lifecycle DRAFT

> **DRAFT — NON-EXECUTABLE.** Prospective policy for owner review. Not
> frozen, not registered, authorizes nothing.

## 1. Dispositions

Every started invocation ends in exactly one **terminal** disposition:

| Terminal disposition | Meaning |
| --- | --- |
| `ADMIT` | A technically evaluable artifact arrived and the evidence contract is satisfied; the artifact is admitted unchanged |
| `FAILURE` | An affirmative, evidenced outcome that no evaluable artifact resulted (e.g. recorded host error, host completed with no image, request not accepted) |
| `INDETERMINATE_FINAL` | The outcome cannot be classified from the available evidence — including interrupted or unknown invocations — and classification is being closed finally |

Two non-terminal states precede a terminal disposition and must never be
reported as outcomes: `PENDING_UNKNOWN`, a started invocation whose outcome
is not yet classified; and an **indeterminate-pending-review** state for an
artifact whose contract compliance is still being decided. Only the three
terminal dispositions above close an attempt. An operator's belief that no
image appeared is never affirmative failure evidence.

## 2. Decision policy (precedence)

Applied in order; the first matching rule decides:

1. **Artifact present and digest-verified, contract satisfied** — all of
   the evidence contract's qualifying requirements Q1–Q5 hold → `ADMIT`.
   The first technically evaluable image is retained; no quality-based
   reroll is permitted, ever.
2. **Artifact present but contract violated** (e.g. wrong digest, extra
   generation in the conversation, edit/regeneration evidenced) →
   indeterminate-pending-review; the artifact is preserved, not silently
   discarded or replaced, and closes as `INDETERMINATE_FINAL` if the
   violation is confirmed.
3. **No artifact, with affirmative no-result evidence** recorded in the
   response capture → `FAILURE`.
4. **No artifact, without affirmative evidence, or invocation interrupted /
   outcome unknown** → `PENDING_UNKNOWN` until terminal classification,
   closing as `INDETERMINATE_FINAL` if it cannot be resolved.
5. **Class-D statements** never decide a disposition. Conflicts between
   class-D reports and authoritative evidence are counted for aggregate
   disclosure and do not change the outcome of rules 1–4.

Retries preserve the frozen v1.1.1 ceiling — at most two retries after a
technical failure, every attempt preserved in order — and are narrowed by
this policy: a retry is permitted **only** after an attempt has closed as
terminal `FAILURE` on affirmative technical evidence. A retry is never
permitted after `PENDING_UNKNOWN` or an unresolved indeterminate state, so
an unknown host outcome can never be re-labelled a technical failure or
quietly retried away; such attempts close as `INDETERMINATE_FINAL` and the
slot is reported incomplete. A retry is a new, separately recorded attempt
linked to its predecessor, never a replacement of it, and never a means to
replace a decodable artifact for quality reasons. Provider safety refusals
are recorded as outcomes, not silently rerolled.

## 3. Attempt and checkpoint lifecycle

1. **Planned** — invocation exists in the frozen plan; no action taken.
2. **Started** — the operator begins the direct-paste workflow; an attempt
   record opens. A started invocation must reach exactly one terminal
   disposition (exactly-once terminal commitment: local recording and the
   external provenance commitment are tracked as separate states so a
   partially committed attempt is detectable and never double-counted).
3. **Artifact or no-result captured** — request/response captures, action
   log, and digests are bound to the attempt.
4. **Terminal disposition committed** — `ADMIT`, `FAILURE`, or
   `INDETERMINATE_FINAL`, with its supporting evidence, committed once.
5. **Run disposition** — when every planned invocation is terminal, or when
   the run is closed incomplete, exactly one terminal `run_disposition`
   event closes the run (proposed decision H3), preserving the existing
   public six-field checkpoint format.

Interrupted invocations stay visibly `PENDING_UNKNOWN` until classified or
forced to `INDETERMINATE_FINAL` at closure; they are never silently dropped
from counts, and incomplete runs are reported as incomplete.

## 4. Terminal attempt receipts and external checkpoints

Each terminal disposition produces exactly one **terminal attempt receipt**,
created once, binding: the invocation's opaque identifier and attempt
number; the terminal disposition; the digests of every supporting evidence
artifact and, for `ADMIT`, of the admitted artifact itself; the class-D
conflict count for the attempt; and the receipt's own predecessor link for
any retry chain. A receipt is never edited after creation; correction is
possible only through the run-closure record, never by rewriting history.

Local recording and external commitment are separate, explicitly tracked
states:

1. **Locally recorded** — the receipt exists in the private run store.
2. **Externally anchored** — a digest-only checkpoint of the receipt is
   committed to the separate provenance repository, preserving the existing
   public six-field checkpoint format and revealing no private evidence.

An attempt counts as committed only when both states hold. If external
anchoring fails, the attempt remains visibly *recorded-unanchored*, the run
pauses (no further invocation starts), and the failure is resolved or the
run is closed incomplete — anchoring is never silently skipped, and a
receipt is never committed twice. The terminal `run_disposition` event is
itself externally anchored in the same six-field format before the run may
be reported.

## 5. Relationship to the scientific rules

This policy governs evidence admission only. It does not alter the preserved
hypothesis, design, rubric, or locked analysis, and a supportive
experiment-level conclusion remains subject to the registered provenance
veto: missing required bindings prevent a supportive conclusion regardless
of any score signal.
