## 2. Proposed run-state machine

### 2.1 States

| State | Meaning |
| --- | --- |
| `CREATED` | Run root exists; not ready for host paste |
| `PREFLIGHT_READY` | Digests, bindings, privacy preflight, BOM probe, scripts self-check OK |
| `ACTIVE` | Owner execution authorized; capture stages permitted within budget |
| `CAPTURE_BLOCKED` | Required capture step failed or evidence incomplete; further progression blocked until owner rule |
| `STOPPED_BY_OWNER` | Owner STOP recorded; local continuation unauthorized |
| `COMPLETED` | All authorized pilots terminal with required artifacts recorded (may still await disposition) |
| `CLOSED` | Owner disposition accepted; immutable under ordinary commands |

### 2.2 Transitions (valid)

```
CREATED → PREFLIGHT_READY          : preflight PASS
PREFLIGHT_READY → ACTIVE           : explicit APPROVE EXECUTION (this run id only)
ACTIVE → CAPTURE_BLOCKED           : required capture failure / invariant breach
ACTIVE → STOPPED_BY_OWNER          : owner STOP
CAPTURE_BLOCKED → STOPPED_BY_OWNER : owner STOP
CAPTURE_BLOCKED → ACTIVE           : ONLY explicit owner UNBLOCK with written scope (rare)
STOPPED_BY_OWNER → ACTIVE          : FORBIDDEN without new owner UNLOCK document (see §2.4)
ACTIVE → COMPLETED                 : budget exhausted or all authorized pilots terminal + evidence sealed
STOPPED_BY_OWNER → COMPLETED       : ONLY if no further capture; closeout of partial run
COMPLETED → CLOSED                 : owner disposition acceptance
CLOSED → *                         : FORBIDDEN via ordinary operator commands
```

### 2.3 Permissions by state

| Command family | CREATED | PREFLIGHT | ACTIVE | CAPTURE_BLOCKED | STOPPED | COMPLETED | CLOSED |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Preflight / BOM probe | ✓ | ✓ | ✓ | ✓ | ✓ (read) | ✓ (read) | ✓ (read) |
| copy / verify-clipboard | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ |
| pre-send / submit / response / download | ✗ | ✗ | ✓* | ✗ | ✗ | ✗ | ✗ |
| attest (unsigned review) | ✗ | ✗ | ✓* | limited† | limited† | ✓ | ✗ |
| attest (sign) | ✗ | ✗ | ✓* | limited† | limited† | ✓ | ✗ |
| owner STOP | ✗ | ✗ | ✓ | ✓ | no-op | ✗ | ✗ |
| status / read-only reports | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| mutate evidence / reopen | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

\*Subject to per-pilot stage gates and remaining budget.  
†Only if needed to seal already-captured artifacts without new host submission; never unlocks new generate.

### 2.4 Post-STOP unlock (explicit only)

If owner later wants continuation on the **same** run id (discouraged):

1. Written `OWNER-UNLOCK-AFTER-STOP.json` naming run id, reason, remaining budget, and exact permitted pilots.  
2. Transition `STOPPED_BY_OWNER → ACTIVE` only after that file validates.  
3. Prefer **new run id** with fresh APPROVE EXECUTION (SHOULD).

Silent inheritance of authorization from a stopped run is **forbidden**.

### 2.5 Trust boundary (local vs host)

| Layer | Enforced by tooling | Not enforced by tooling |
| --- | --- | --- |
| Local capture commands, run state, budget counters, evidence writes | Yes | — |
| ChatGPT Images UI clicks / generates | — | Operator can still click Generate in browser |
| Preventing host-side generation after STOP | — | **Cannot**; tooling must refuse to record authorized continuation and must log attempts |

UI and checklist must state: **local enforcement ≠ host lock**.

## 4. Explicit trust and enforcement boundaries

1. **`operator_observed` timestamps** are wall-clock times of local capture commands (or explicit operator entry). They **do not** prove exact ChatGPT host submit/response instants.  
2. Tooling **can** refuse to write authorized evidence and refuse local progression.  
3. Tooling **cannot** disable ChatGPT Images. Post-STOP host clicks remain possible; they must not be laundered into authorized contemporaneous success.  
4. Q5 attests operator-confirmed **host/capture facts**, not authorization compliance, unless separate statements are added in a future protocol revision (out of scope for silent addition).  
5. Closed runs: ordinary commands are read-only; corrections use append-only superseding documents (as done for follow-up reconciliation).

## 6. Operator workflow design (guided stages)

Single entrypoint (SHOULD): `.\tools\g3_operator.ps1` showing banner each stage:

- Current pilot id  
- Current run state  
- Remaining authorized submissions  
- Required human action  
- Evidence recorded this stage  
- Proceed permitted? (yes/no + reason)

| Stage | Name | Human action | Tooling | Auto-generate? | Auto-confirm Q5? |
| --- | --- | --- | --- | --- | --- |
| 1 | PREPARE | Confirm host Images UI; record label | state→ACTIVE checks | No | No |
| 2 | VERIFY PROMPT | Copy + verify clipboard | digest match | No | No |
| 3 | RECORD PRE-SEND | Run pre-send **before** Generate | write pre-send | No | No |
| 4 | SUBMIT AND RECORD | Click Generate once; **immediately** run submit | Q1 contemporaneous | No | No |
| 5 | RECORD RESPONSE | When image visible, run response | Q2 | No | No |
| 6 | VERIFY DOWNLOAD | Save file; provide path (quoted) | Q4 hash/raster | No | No |
| 7 | REVIEW AND SIGN | Read statements; CONFIRM + signature | UNSIGNED then SIGNED | No | No |
| 8 | COMPLETE | Owner disposition / next pilot or STOP | state transition | No | No |

If any stage fails: enter `CAPTURE_BLOCKED` or remain non-permitted; display “do not continue host generates.”
