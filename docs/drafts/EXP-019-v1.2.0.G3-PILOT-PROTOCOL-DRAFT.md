## 0. Purpose and hard separation

The pilot proves the v1.2 **evidence workflow** end to end on a live host
using **non-experimental** material only: direct paste, contemporaneous
captures, digests, admission decisions, and privacy checks.

The pilot is **not** a small experiment:

- Pilot prompts, images, and evidence **never** enter the experimental sample.
- Pilot outputs are **never** reviewer-scored for science.
- Nothing learned may alter the preserved hypothesis, design, rubric, or
  locked analysis.
- Pilot identifiers are disjoint from experimental and synthetic E2E slot
  alphabets used for the 12-sample scientific design.

## 4. Request, response, download, and attestation handling

1. **Request:** paste bytes captured immediately; no prompt file upload.
2. **Response:** captured when the host returns an image, confirms failure, or
   the operator records observed absence / interruption / unknown.
3. **Download:** only the host-provided file bytes; no re-export through
   editors that alter pixels or metadata if avoidable; if metadata strip is
   required for a later scientific path, pilot still hashes the **downloaded**
   bytes as returned for Q4 unless the protocol packet says otherwise
   (pilot packets: hash downloaded bytes as returned).
4. **Attestation:** operator attests digests and no-edit claims only for
   artifacts that exist; never attest a missing output.
5. **Class-C:** optional; missing class-C must not be forged. Unsolicited
   model statements → class-D only, never elevated to authenticated host
   telemetry.
6. **Class-D conflicts:** preserved on ADMIT; never dropped to beautify a
   pilot report.

## 5. Prospective success, failure, and indeterminate criteria

Fixed **before** execution (admission engine semantics; pilot labels only):

| Outcome class | When | Pilot accounting |
| --- | --- | --- |
| **Success (workflow)** | Evidence eligible; disposition `ADMIT`; digests verify; privacy scan clean | Counts toward pilot exit as a successful **workflow** exercise — **not** an experimental sample |
| **Technical failure** | Confirmed host technical failure / invalid raster / protocol violation per admission | Counts as exercised failure path; retry only if admission marks retry-eligible **and** prior attempt externally anchored per PR-9 rules |
| **Pending unknown** | Interrupted / unknown host outcome | Must **not** become technical failure or ADMIT by operator testimony alone; may later close only via authorized indeterminate procedure if owner authorizes that closure for the pilot |
| **Indeterminate final** | Explicit H3-style authorization for the pilot invocation | Terminal for that invocation; never “completed experiment” |
| **Non-admission with B/C conflict** | Authenticated material B/C conflict | Must not ADMIT; record for pilot report |

**Pilot success (gate exit)** ≠ scientific completion. No 3×4 design, no
reviewer freezes, no locked analysis on pilot scores (pilot is never scored).

## 6. Abort and interruption handling

**Abort the pilot immediately if any of:**

1. Experimental EXP-019 prompt bytes, treatment wording, or allocation ids
   appear in pilot packets, logs, or public artifacts.
2. Operator attaches a prompt file or edits the frozen paste.
3. Evidence is reconstructed or fabricated for a missing capture.
4. Class-C is forged or unauthenticated host claims are treated as class-C.
5. A pilot image is placed under an experimental run root or reviewer package.
6. v1.2 is registered or an experimental allocation/run root is created.
7. Git push targets a production provenance remote.
8. Any attempt to score pilot images under the scientific rubric.

**Interruption:** leave outcome `PENDING_UNKNOWN` or incomplete per
lifecycle; do not invent no-result captures. Resume only the same pilot
invocation identity; never start a new generation and pretend it is the
same attempt.
