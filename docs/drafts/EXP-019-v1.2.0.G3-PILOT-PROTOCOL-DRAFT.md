## 0. Purpose, representativeness, and hard separation

The pilot proves the v1.2 **evidence workflow** end to end on a live host
using **non-experimental** material only: direct paste, contemporaneous
captures, digests, admission decisions, and privacy checks.

The pilot is **not** a small experiment:

- Pilot prompts, images, and evidence **never** enter the experimental sample.
- Pilot outputs are **never** reviewer-scored for science.
- Nothing learned may alter the preserved hypothesis, design, rubric, or
  locked analysis.
- Pilot identifiers are disjoint from experimental and synthetic E2E slot
  alphabets used for the 12-sample scientific design.

**Limited representativeness (disclosed):** this protocol authorizes at most
**two** live pilot prompts (`PLTA01`, `PLTB01`). That is **not** a
scientific 3×4 design, does **not** sample experimental treatments, and
cannot establish production readiness, human reviewer independence, or
scientific findings. Passing the pilot only supports G3 workflow evidence.

## 2. Fixed non-experimental pilot prompts (exact bytes + digests)

**Independence rule:** prompts contain **none** of: Japanese woodblock,
bokashi, riverbank/bridge/pine composition, indigo/light-blue treatment
region wording, EXP-019 treatment clauses, allocation vocabulary, or
condition labels C/A/B as treatments.

**Encoding:** UTF-8, no BOM, LF (`\n`) newlines only, **exactly one**
trailing newline on the canonical body. Digests are SHA-256 of those bytes.

### 2.1 Prompt order, count, stopping rules, retry policy (fixed)

| Rule | Fixed value |
| --- | --- |
| Order | **PLTA01 first**, then **PLTB01** (if authorized by the invocation budget below) |
| Maximum authorized live generation submissions | **2** (one per prompt id), plus at most **2** technical-retry submissions total across the pilot if and only if admission marks the prior attempt retry-eligible **and** the prior attempt is externally anchored per PR-9 rules |
| Absolute ceiling | **≤ 4** host generation submissions for the entire pilot run |
| Stopping — success path | After PLTA01 reaches a terminal disposition, proceed to PLTB01 only if remaining budget allows and the owner’s execution authorization did not restrict the run to PLTA01-only |
| Stopping — complete | When both started prompts are terminal **or** abort triggers fire **or** the absolute ceiling is reached |
| Minimum for pilot-report exit eligibility | At least **PLTA01** terminal; PLTB01 is part of the fixed plan when the execution authorization selects the **two-prompt** profile (default). Owner may authorize a **PLTA01-only** profile in the execution packet without rewriting prompts |
| Retry | Never by operator convenience. Retry only when the admission decision sets `retry_eligible=True` for a confirmed technical failure and anchor verification is a real PR-9 `VerificationResult`. Unknown / pending outcomes are **never** retried as technical failures |
| No post-hoc flexibility | Operators may not swap prompts, reorder, add a third prompt, or raise the ceiling without a new protocol revision and fresh owner review |

## 5. Request, response, download, and attestation handling

1. **Request:** paste bytes captured immediately; no prompt file upload.
2. **Response:** captured when the host returns an image, confirms failure, or
   the operator records observed absence / interruption / unknown.
3. **Download:** only host-provided file bytes; no editor round-trip that
   alters pixels; hash downloaded bytes as returned.
4. **Attestation:** only for artifacts that exist.
5. **Class-C:** optional; missing class-C must not be forged. Unsolicited
   model statements → class-D only.
6. **Class-D conflicts:** preserved on ADMIT; never dropped.

**Unknown outcomes:** operator-observed absence or interruption without
authenticated host confirmation remains `PENDING_UNKNOWN` (or incomplete).
It **must not** be reclassified as a confirmed technical failure by
operator testimony alone.

## 6. Prospective success, failure, indeterminate, and abort criteria

| Outcome class | When | Pilot accounting |
| --- | --- | --- |
| **Success (workflow)** | Evidence eligible; disposition `ADMIT`; digests verify; post-execution leak scan clean for that invocation’s public exports | Workflow exercise only — **not** an experimental sample |
| **Technical failure** | Confirmed host technical failure / invalid raster / protocol violation per admission | Failure path; retry only under §2.1 |
| **Pending unknown** | Interrupted / unknown host outcome | Never auto-failure; no technical retry from testimony alone |
| **Indeterminate final** | Explicit H3-style authorization for **that pilot invocation** | Terminal for invocation; never “completed experiment” |
| **Non-admission (B/C conflict)** | Authenticated material B/C conflict | Must not ADMIT |
| **Abort** | Any §7 trigger | Stop all further submissions; preserve evidence collected |

**Pilot success (gate exit)** ≠ scientific completion.

## 7. Abort and interruption handling

**Abort the pilot immediately if any of:**

1. Experimental EXP-019 prompt bytes, treatment wording, or allocation ids
   appear in pilot packets, logs, or public artifacts.
2. Operator attaches a prompt file or edits the frozen paste.
3. Evidence is reconstructed or fabricated for a missing capture.
4. Class-C is forged or unauthenticated host claims are treated as class-C.
5. A pilot image is placed under an experimental run root or scientific
   reviewer package.
6. v1.2 is registered or an experimental allocation/run root is created.
7. Git push targets a production provenance remote.
8. Any attempt to score pilot images under the scientific rubric.
9. Prompt digest mismatch vs §2.
10. Host image-generation surface unavailable or operator cannot record
    `host_ui_label_observed`.
11. Invocation budget / absolute ceiling would be exceeded by the next
    submission.

**Interruption:** leave `PENDING_UNKNOWN` or incomplete; do not invent
no-result captures. Resume only the **same** pilot invocation identity;
never start a new generation and claim it is the same attempt.
