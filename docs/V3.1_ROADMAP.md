# Recommended V3.1 Milestone — Evidence Graph + Regression Harness

V3.0 proves the architecture. V3.1 should **not** respond by adding hundreds of prompts.

## Priority 1 — Compatibility/evidence graph

Replace broad per-pack incompatibility lists with typed facts that can answer questions such as:

```text
Ming + elite woman + garden + summer + hair ornament + specific garment
Edo + Hizen/Arita blue-and-white + plate + portrait medallion
Tang-period Mogao + donor figure + specific cave family + mural state
Roman 2nd c. + private portrait + bronze bust + hairstyle family
```

Each fact should carry source, date range, region, role, compatibility, confidence and notes. The gate can then reason across individual visible elements rather than only pack-level warnings.

## Priority 2 — Sample-output ingestion

Build an ingestion tool for the upgraded Image Library that:

1. hashes and catalogs the 606 sample images;
2. links an image to source prompt/collection when known;
3. labels what the sample actually validates: pose, identity, layout, material, historical detail, or only aesthetic quality;
4. selects a small set of representative images into golden/regression cases instead of copying the entire library.

## Priority 3 — Vision evaluator adapter

Add host-native evaluation adapters that produce `evaluation.schema.json` records from generated images. Do not collapse them into one beauty score. The evaluator should cite visible evidence and assign failure classes.

## Priority 4 — Era depth, not breadth

Deepen the current scope before adding the whole world:

- Tang: early/high/late Tang + status/occasion wardrobe and hair evidence.
- Dunhuang: selected cave/subperiod packs with iconographic zones and pigment/surface notes.
- Ming: early/mid/late, civilian vs court, grounded wuxia compatibility.
- Edo: decade/class/occupation + Arita/Hizen ceramic submodule.
- Greek/Roman: date-sensitive hair, dress, portrait conventions, sculptural polychromy/state.

## Priority 5 — Regression runner

For each golden case, store:

- semantic spec hash;
- compiler version;
- prompt hash;
- model snapshot/version;
- input reference hashes;
- output image hash;
- evaluation scores/failures;
- revision history.

Then a V3.1 release can answer a real engineering question: **did this change make the system better or merely different?**
