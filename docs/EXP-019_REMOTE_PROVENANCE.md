# EXP-019 remote provenance checkpoints

EXP-019 execution requires `AIPF_EXP019_PROVENANCE_REMOTE` to contain a Git remote URL or filesystem path that accepts creation and ordinary fast-forward pushes to `refs/heads/exp-provenance/<run-id>`; a nickname such as `origin` is not resolved inside the temporary Git repository. Git credentials and ref policy are provided by the operator. The application neither checks out this ref nor pushes checkpoint records to `main` or the implementation branch. An unset or unavailable remote blocks execution.

Before the first generation action, the tool pushes a root checkpoint for the frozen private run plan. For v1.1.0 host-native execution, every imported attempt binds its event prefix, operator attestation and source-origin declaration, canonical receipt, and any decodable raster and measured metadata before the next attempt or slot. The archived v1.0.0 API path retains its provider receipt and commitment bindings. A retry waits for verification of all earlier checkpoints. Each reviewer freeze has its own checkpoint binding the frozen review, private mapping, and local commitment bytes. The private mapping also binds each canonical raw output to a metadata-free, pixel-equivalent reviewer PNG. Reveal requires both remote freeze checkpoints. Receipt and result validation fetch and verify the chain again.

Each remote commit contains **only** `checkpoint.json` with `schema_version`, `run_id`, `sequence`, `event_type`, `evidence_sha256`, and `previous_anchor_commit`. The remote ref's name contains the run ID. Git commit metadata uses a fixed non-sensitive author and message. The ref exposes checkpoint count and timing, but no slot ID, treatment label, prompt or prompt hash, output hash, private mapping, reviewer ID, score, diagnostic, failure flag, or raster. The private run directory retains the mapping from checkpoints to evidence. Do not give reviewers access to that directory before both reviews are frozen.

The tool fetches the remote ref before appending or accepting evidence. It requires the expected head, one-parent linear commits after the root, exact checkpoint sequence, and exact digests of current private evidence. It pushes without force and verifies the new remote head. It does not reconcile divergent histories. A missing ref, missing local index, rewritten local evidence, or remote advancement blocks the next critical operation. If a push succeeds but saving the local checkpoint index fails, the mismatch blocks continuation and requires manual provenance-invalid handling; it is never silently retried.

The remote Git ref is the integrity trust boundary. This protects against replacing local receipts, run ledgers, freeze commitments, reviews, or their local hashes after their checkpoint was pushed. It also prevents the application's ordinary workflow from force-updating or merging the provenance chain. It cannot protect against compromise of the remote host, deliberate administrative ref deletion or replacement outside the protocol, modification of the software before execution, or an operator redirecting the trusted remote configuration. Ref protection and access control are operational requirements for a real run. A temporary bare Git remote is used only in offline tests.
